# 🕵️ 逆向拆解与对抗审查（挑刺）

## 1. 你要解决的问题

“挑刺”不是列一串问题，也不是判断文字像不像 AI 写的。

你的任务是回答：

> 一个项目声称“方案成立 / 功能完成 / 测试通过 / 交付可用”时，能不能从用户最终结果反向追到真实路径，并用最低成本证明这句话不是纸面成功？

它防的是任何执行者（包括人和 AI）用漂亮文字、局部测试、旧输出或自制报告冒充完成。

核心链路：

```text
用户结果
  ↓ 反向追问
可观察行为
  ↓
真实入口和工作流
  ↓
关键机制与依赖
  ↓
失败、恢复和边界
  ↓
最小独立证据
  ↓
结论强度
```

## 2. 总原则

### 2.1 先问最终结果，不先看实现

先说清楚：

- 谁使用；
- 从哪个入口开始；
- 执行什么动作；
- 完成后用户实际看到或得到什么；
- 什么情况算失败；
- 哪些内容明确不在本次范围内。

没有可观察结果，不能开始“已完成”判断。

### 2.2 从结果反推，不按文件顺读

普通顺读容易被代码、目录和报告带着走。固定从最后一句主张开始追问：

```text
“已经可用”
  → 用户从哪里使用？
  → 哪个动作触发？
  → 哪个结果证明生效？
  → 失败时用户看到什么？
  → 重试/恢复后是否仍成立？
```

### 2.3 风险驱动，不跑固定清单

不要默认逐项执行长清单。先从当前项目选最可能的 2-3 个假绿或失败路径，再按证据需要扩展。

没有风险理由，不新增检查；已有决定性证据，不重复堆审查层。

### 2.4 证据强度不能低于结论强度

结论使用四态：

- **通过**：在声明范围内已有足够证据。
- **有条件通过**：核心路径成立，但有不影响当前范围的已知限制。
- **阻塞**：关键路径或关键证据失败，不能交付或不能继续声称完成。
- **证据不足**：当前无法判断，不把未知写成通过或失败。

证据状态另行标记：

- **已确认**：有直接观察或可重复实验，并且判据已经自证。
- **高概率风险**：证据已指向问题，但还缺独立复核。
- **待验证**：有合理疑点，当前证据不足。
- **未检查**：超出本次范围，不能写成“没有问题”。

禁止把“我读过了”“测试跑过了”“文件存在”直接写成“已完成”。

### 2.5 先找最便宜的决定性检查

每个疑点先问：

> 哪个最小实验可以最快区分“真的生效”和“只是看起来生效”？

如果一个命令、一个反例或一次真实入口演练已经能决定结论，就停止扩展。复杂不等于认真。

## 3. 五步逆向审查

### 第一步：锁定主张（Claim）

把“做完了”“能用了”“测试通过”改写成可证伪句子：

```text
主张：在 [范围] 内，用户从 [入口] 执行 [动作] 后，会得到 [可观察结果]；遇到 [关键失败] 时，不会出现 [不可接受后果]。
```

至少写出：范围、入口、结果、关键失败、不在范围内的部分。

如果主张无法写清，结论就是“需求/定义未闭合”，不能进入实现验收。

### 第二步：逆向拆链（Reverse Decomposition）

从用户结果向后画最短链：

```text
结果
→ 触发动作
→ 真实入口
→ 关键步骤
→ 依赖和前置条件
→ 数据/输入来源
→ 失败出口
→ 恢复或回滚
```

每层只回答：

1. 这一层如果不工作，用户会看到什么？
2. 什么证据能证明这一层真的工作？

不能说明“这一层解决哪个具体失败”的额外机制，先列为可疑复杂度。

### 第三步：选择对抗路径（Attack Selection）

优先从下面六类中选择与当前项目最相关的 2-3 类：

1. **纸面成功**：报告说完成，但用户真实入口不可用。
2. **局部成功**：内部函数或单个样例通过，完整链路失败。
3. **静默降级**：主机制失效，却仍输出看起来正常的结果。
4. **范围偷换**：抽查少数样本，却声称整个项目成立。
5. **自证循环**：测试、报告和被测对象使用同一来源，无法独立证明。
6. **失败后失控**：重试、中断、回滚或恢复时丢数据、重复执行或状态错误。

对每条路径写清：

```text
如果执行者想用最低成本假装完成，最可能怎么做？
用户如何最快发现？
哪个实验能让这个假象失败？
```

### 第四步：构造证据（Proof）

重要主张至少需要一个直接证据；高风险红灯必须有第二种独立证据。

证据优先级：

1. **真实入口演练**：从用户入口执行并观察结果。
2. **故障注入**：破坏一个前置条件，确认失败/降级可见。
3. **反例测试**：用已知坏输入，确认判据确实会响。
4. **独立交叉检查**：更换来源、脚本或观察方式复核。
5. **静态阅读**：只能证明代码/文档声称如此，不能单独证明运行时成立。

反向证据纪律：

- 得出“没有问题”前，先用已知有问题样本确认检查器会命中；
- 测试通过前，先确认测试对已知坏版本确实会失败；
- 红灯结论必须由第二种独立判据复核；
- 证据来源不能与被测结果完全同源；
- 测试和检查不能污染被测对象；
- 引用数字、版本、时间、路径和输出必须来自实际读取或命令结果；
- 发现判据自身可能错误时，先查判据，再归因于被测对象。

### 第五步：做出裁决（Verdict）

每个结论必须对应一个主张，并同时列出：证据、剩余风险、下一步最小动作。

不要用“全绿、无遗漏、已彻底修复、全部通过”等整体性词语，除非同时枚举完整范围和证据来源。

## 4. 防偷懒与防 AI 作弊

这里的“防 AI 作弊”不是检测文风，而是让没有真实工作和证据的回答无法通过。

### 4.1 防文字改写冒充完成

以下内容不算证据：

- 重复用户需求；
- 重述设计目标；
- 说“已实现 / 已修复 / 已验证”但无可复核动作；
- 用计划、注释、README 或截图代替运行结果；
- 把“应该做”写成“已经做”。

### 4.2 防测试作弊

测试必须能区分好坏：

- 已知坏样本必须让测试失败；
- 不能只测 happy path；
- 测试对象应经过真实入口或最高层公共接口；
- 测试夹具不能偷偷绕过被测路径；
- 测试输出不能由测试脚本自己拼成成功结论；
- 测试结束后要确认测试没有修改被测对象或关键证据源。

### 4.3 防数据作弊

禁止：

- 只挑通过样本；
- 修改输入后继续使用旧结果；
- 使用未声明的人工修正数据；
- 用汇总数字掩盖样本范围；
- 用旧版本、旧时间或 stale 报告证明当前状态。

必须写清：样本来源、样本数量、检查时间、参数、版本和是否可复现。

### 4.4 防范围偷换

每次结论都要说明：

```text
检查了什么 / 没检查什么 / 检查到哪一层 / 哪些假设未验证
```

没有枚举范围时，不使用“全部、全绿、无遗漏、全都在、已彻底修复、测试链通过”等整体性结论。

### 4.5 防复杂度偷懒

新增一层机制前必须回答：

1. 不加这一层，哪个具体失败无法被发现或修复？
2. 是否有更短的直接实验可以替代？
3. 这一层本身如何证明生效？
4. 失败时是否能安全回退？

答不出第一问，默认不加。

### 4.6 防审查走过场

不要先写长报告。先给出：

- 最可能的一个假绿点；
- 最小决定性实验；
- 当前是否阻塞。

只有用户要求全面审查、发现阻塞、涉及安全/数据丢失/迁移/不可逆操作，或第一轮证据冲突时，才升级深审查。

## 5. 按项目阶段使用

### 5.1 方案阶段

先输出：

```text
目标结果：
最短工作流：
最大风险：
最小验证实验：
不做什么：
```

先回答“怎么证明有用”，再讨论模块、字段和层次。

### 5.2 实施阶段

实施前建立挑战卡：

```text
主张：
真实入口：
成功判据：
已知坏样本：
故障注入：
独立复核：
回滚/恢复：
```

实施后至少证明：坏样本红灯、正常路径绿灯、真实入口可用、未检查范围已列出。

### 5.3 交付阶段

从干净或接近干净的用户环境执行一次：

- 正常入口；
- 参数透传；
- 退出码或可观察结果；
- 至少一个错误路径；
- 产物是否出现在用户预期位置。

“本机某命令能跑”不等于“用户可以使用”。

### 5.4 事故阶段

顺序固定：

```text
复现事故
→ 确认判据能捕获事故
→ 找最短断点
→ 验证修复前红灯
→ 验证修复后绿灯
→ 检查相邻路径未被修坏
```

### 5.5 AI 产物阶段

审查文档、分析、代码、计划、报告或回答时，重点检查：

- 引用是否真的存在；
- 结论是否超出来源范围；
- 数字能否重算；
- 是否遗漏反例和不确定性；
- 是否把建议写成事实；
- 是否把计划写成已完成；
- 是否只展示了有利样本。

## 6. 默认输出格式

默认先输出一屏：

```markdown
## 结论
通过 / 有条件通过 / 阻塞 / 证据不足

## 最大风险
- [风险]：为什么它最可能造成假绿或实际失败

## 最小验证
- [动作]：预期看到什么；看到什么才算失败

## 已确认
- [证据]

## 未确认 / 范围外
- [项目]

## 下一步
- [一个最小动作]
```

复杂审查才追加：逆向链路图、风险矩阵、发现明细、证据清单、修复后复查和可复用经验。

通用技能不强制固定文件路径、报告目录、daily、状态文件或项目回流动作。用户要求落盘时，写入当前项目已有约定的位置；没有约定时只返回审查结果，不擅自修改项目文档、状态、配置或数据。

## 7. 只读边界与修复边界

默认是只读审查：可以读取项目、运行不改变状态的检查和临时沙箱实验，可以写临时证据或用户要求的审查报告，但不得擅自修改项目产物。

发现问题后：

- 用户只要求审查：报告问题和最小修复建议，不修改；
- 用户明确要求修复：先说明修复范围，再修改；
- 修改不可逆内容：先备份或建立可回滚点；
- 修复完成：必须重新执行与主张对应的红灯、绿灯和相邻路径检查。

审查报告本身不是功能证据，也不自动代表用户批准了修复。

## 8. 项目适配边界

通用技能只保留以下方法：

- 逆向拆链；
- 风险驱动选查；
- 最小决定性实验；
- 判据自证；
- 红灯独立复核；
- 反自污染；
- 证据强度约束结论；
- 修复前后双侧验证；
- 范围和未验证项显式化；
- 达到决定性证据后停止。

以下内容属于项目适配，不得写死进通用技能：

- 项目目录、命令、测试编号和守卫编号；
- 项目专用报告路径和状态回流；
- 宿主、挂载位、MCP、模型和数据格式；
- 项目特定的固定检查清单。

适配层只说明“本项目如何执行通用方法”，不改变通用技能的证据标准。

## 9. 审查停止条件

满足以下任一条件即可停止：

- 已找到阻塞问题；
- 已有足够证据做出通过或有条件通过；
- 剩余未知不改变当前决策，继续检查的收益低于成本；
- 用户要求停止。

不能为了覆盖更多类别而无限延长审查。

## 10. 技能自身的反向验收

重写后的技能必须能识别以下故意问题：

- 只有 README 声称完成，没有真实入口；
- 只测 happy path，坏样本不会失败；
- 测试夹具绕过真实入口；
- 抽查两个样本却声称全部通过；
- 使用旧测试输出证明新版本；
- 复杂方案无法说明新增层的必要性；
- 报告把建议写成已完成事实；
- 审查报告很长，但没有最小决定性实验；
- 检查器对已知坏样本不报警，却把零命中写成“没有问题”。

若无法对这些样本提出具体验证动作，说明技能仍在检查文案，不是在做对抗审查。

## 11. 技能定位

> **逆向拆解与对抗审查（挑刺）**：从用户最终结果反向追踪真实入口、关键机制和失败出口，优先寻找最可能造成纸面成功、局部成功、静默降级、范围偷换和自证循环的路径。只用可复核证据下结论，不把计划、文件存在或测试自述当成完成证明。适用于方案、代码、数据、流程、交付物和 AI 产物；默认短审查，按风险升级，不绑定任何项目结构。
